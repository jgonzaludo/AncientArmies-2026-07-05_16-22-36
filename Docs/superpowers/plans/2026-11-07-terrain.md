# Terrain Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace the flat sand plane with a painted-map terrain system (grass, road, mud, ford, river, rock, forest, bridges) that changes formation speed, blocks routes, and looks like the approved mockups.

**Architecture:** A `TerrainMap` ScriptableObject turns a hand-painted PNG into a grid. Gameplay reads the grid (speed, blocked, concealed); a grid A* planner sits in front of the existing circle `RoutePlanner`; a presentation-only `TerrainView` builds the ground, props, water and lighting at runtime. `Battle.unity` is never edited: everything is created from code, and the active map loads from `Resources` unless a new `BattleSetup` field overrides it.

**Tech Stack:** Unity 6000.4.8f1 URP, C#, KayKit Forest Nature Pack (CC0), editor tasks driven by the file-trigger harness (`Temp/scenario_request.txt`).

**Spec:** `Docs/superpowers/specs/2026-11-07-terrain-design.md`. Target look: `ArtSource/References/terrain_mockups/`.

## Global Constraints

- Field is 410 x 340 m (`fieldHalfX` 205, `fieldHalfZ` 170); grid cell 2 m (205 x 170 cells).
- Starting speed multipliers: road 1.15, grass 1.0, forest 0.7, mud 0.6, ford 0.5; deep water and rock blocked.
- `Formation` is the only writer of `AnchorPos`/`AnchorRot`; commanders only call `Issue*`; visuals read, never drive gameplay.
- `Battle.unity` must not be edited or saved; new serialized values go in new fields or assets, never as changed C# defaults.
- Scripts flat in `Assets/Scripts`, one public type per file; editor code in `Assets/Editor`; `Resources.Load` names are exact.
- Third-party art in `Assets/ThirdParty/KayKit/Forest` with its license copied to `Assets/ThirdParty/KayKit/Licenses`. Reference images stay under `ArtSource/`.
- No fog of war, hills, weather, random generation, backend. Lighting stays near current; no mobile-costly shadows.
- Test at 2x speed or below with cameras on. Nothing is committed until the owner has played and approved it.
- Casual lowercase code comments, no em dashes in docs or UI copy.

## Review Focus

- A move order dropped on deep water or rock: expected to snap to the nearest reachable walkable spot, never to stall the formation.
- A destination on an unreachable island (no path): expected to snap to the nearest reachable cell, AI never targets it.
- Formation starting on slow or blocked ground at battle start: expected to be walkable by map validation.
- A formation wider than a bridge or ford: expected to still cross (bridges painted at least one formation wide).
- Anchor sitting exactly on a cell border: expected smooth speed, no flicker between two multipliers.
